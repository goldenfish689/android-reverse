# 帧布局与消息字段

从相同方向的多条消息开始，记录偏移、长度、端序、候选类型、支持该判断的样例编号。首先检验长度字段是否包含头部、校验字段或压缩前长度。

| 候选结构 | 需要验证的证据 |
|---|---|
| 定长头 + 变长体 | 不同长度样例的边界是否都成立 |
| TLV | type、length、value 的连续性与未知类型处理 |
| Protobuf | wire type、字段号与客户端 serializer 是否匹配 |
| 压缩体 | 解压后结构、长度及失败行为 |
| 带认证数据的密文 | IV/nonce、tag、AAD 与调用处是否一致 |

Protobuf 原始解码只能提供字段号和 wire type 线索，不能自动恢复字段名称或区分所有业务类型。应对照生成类、描述符或调用者；没有证据就保留未知名。

离线解析器需要区分“尚未收全”与“无效消息”，检查长度上限并返回消费字节数，避免超大长度分配。至少用截断头、截断体、两帧拼接和未知类型验证边界。

PCAP 中按包导出的 `tcp.payload` 适合查看线索，正式消息还原需处理 TCP 重组、重传和方向；不能直接按行拼接后当成可靠业务流。

最终记录会话起止、认证、心跳、重连和请求/响应关联。只有用户需要线上重放时，才额外验证会话凭证、时间窗、nonce 与服务端状态。
